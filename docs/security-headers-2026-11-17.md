# Saitena HTTP security headers — 17 November 2026

Baseline: live main `54909bc8d12a7c1e235c1950b68ffbc80943ecf0`.
Branch: `codex/http-security-headers`. No production change is included in this audit.
The footer correction remains a separate PR #4.

## Observed responses and responsibility

Read-only GET probes checked 26 HTTPS responses through Cloudflare: apex and www,
home/FAQ/prices/contact, health, robots, CSS/JS, PNG, optimized image and denied
legal/media paths. Node TLS validation was enabled. Both HTTP roots return 308
to the corresponding HTTPS hostname. No TLS/subdomain-wide change is proposed.

All four scanner findings are confirmed on ordinary HTML responses. Direct app
loopback probes through existing administrative SSH reproduce the missing headers;
they are not generated by Next.js. The existing public/www Caddy block has no
XFO/nosniff/HSTS/CSP directives. The active Caddy configuration matches its source.
Other hostnames have their own headers; none of those settings was edited.

Exception: `/_next/image` already sends the enforcing policy
`script-src 'none'; frame-src 'none'; sandbox;`. Its value is identical at the app
and Cloudflare edge. It is preserved. This demonstrates that CSP is not universally
stripped by the edge; new-header forwarding still requires verification after an
owner-approved deployment. No Cloudflare account setting was changed or assumed
to be a substitute for measuring the actual response.

Legal and unapproved-media paths return real 404 responses. An arbitrary unknown
page currently returns streamed not-found content with HTTP200; that pre-existing
status behavior is recorded and is outside this header correction.

## Before / candidate

“After” below is a tested local production candidate, not a claim about live production.

| Header                              | Live ordinary HTML before                       | App candidate after                  |
| ----------------------------------- | ----------------------------------------------- | ------------------------------------ |
| X-Frame-Options                     | absent                                          | `DENY`                               |
| X-Content-Type-Options              | absent                                          | `nosniff`                            |
| Strict-Transport-Security           | absent                                          | `max-age=300`                        |
| Content-Security-Policy-Report-Only | absent                                          | exact diagnostic policy below        |
| Content-Security-Policy             | absent on HTML                                  | deliberately not enforced yet        |
| Next Image Content-Security-Policy  | `script-src 'none'; frame-src 'none'; sandbox;` | unchanged                            |
| X-Robots-Tag                        | `noindex, nofollow, noarchive`                  | unchanged                            |
| Cache-Control at public edge        | `private, no-store`                             | existing app/edge behavior unchanged |

Exact Report-Only policy:

```text
default-src 'self'; base-uri 'self'; object-src 'none'; frame-ancestors 'none'; script-src 'self'; script-src-attr 'none'; style-src 'self'; style-src-attr 'none'; img-src 'self' data: https://tile.openstreetmap.org; font-src 'self'; connect-src 'self' https://api.saitena.com; frame-src 'none'; worker-src 'none'; media-src 'none'; manifest-src 'self'; form-action 'self'
```

The only cross-origin allowances are the source-defined OSM tile hostname and the
existing authentication API. Links to Google Maps/Viber are navigation links and
need no iframe/script exemption. Fonts, scripts and stylesheets are served locally;
embedded raster SVGs and image placeholders justify `data:` for images only.
There are no wildcard script sources, `unsafe-inline`, `unsafe-eval`, fixed nonces,
or arbitrary external collectors. HSTS has no includeSubDomains or preload.
Its initial five-minute lifetime limits rollback persistence. HSTS/CSP diagnostics
are omitted in development; development exceptions are not copied into production.

The shared policy module is imported by Next config and existing CI assertions.
Security headers remain present even if indexing is enabled in a future approved
public configuration; current noindex remains enabled.

## CSP observations and staged enforcement proposal

Chrome157.0.8103.38 with valid trusted local HTTPS checked eight main routes at
375px and1366px: **16 route/viewport checks**. It scrolled content/lazy images,
opened FAQ, exercised mobile navigation and reloaded saved dark/120% preferences.
There were no page/hydration errors, failed resources, broken visible images or
horizontal overflow. Report-Only emitted **118 inline script** and **298 inline
style-attribute** violations in this recorded sample; all had disposition `report`.
The number is sample-dependent, not a promised site-wide daily total.

Source inspection attributes inline scripts to theme/text-size bootstrap and
React/Next streaming/RSC payloads. Inline style attributes occur in the existing
menu/card animation delays, appearance popup coordinates and illustration styles.
No external script/font origin or eval exception was needed in the tested build.
Cloudflare Email Obfuscation/other edge-injected content needs a fresh edge browser
check after the separately approved Report-Only rollout. The current sample does
not prove that every production/user/browser path has been observed.

There is no report collection endpoint, third-party reporting service or report
body logging. Observations were captured via `securitypolicyviolation`/DevTools
in isolated test browsers. Do not claim central monitoring of real visitors.

XFO enforcement was tested independently: the candidate produces a Chrome blocked
iframe; the same built document/report-only framing policy without XFO renders.
Chrome's diagnostic wording was not used as the sole pass condition.

After reviewing these violations, the **separate, not activated** initial enforcing
proposal for HTML is:

```text
Content-Security-Policy: base-uri 'self'; object-src 'none'; frame-ancestors 'none'
```

That proposal was locally tested on home/FAQ at both widths: four successful page
checks with zero enforcing violations. It also blocks framing with XFO removed.
It leaves scripts/styles under Report-Only while strict compatibility is addressed.
It is not a complete script-injection/XSS policy. Preserve Next Image's distinct
sandbox policy rather than replacing it with this HTML policy.

Promoting the complete diagnostic policy now would block Next's required inline
scripts/styles. A strict script policy requires reviewed per-document hashes for
static HTML/streaming and style handling, or properly per-request nonces with
dynamic rendering. The latter changes the current static/performance architecture
and needs its own review. No unsafe blanket exception is added to obtain a scan score.
This PR intentionally leaves enforcing HTML CSP for a separate owner-approved stage;
a scanner requiring that header may continue to flag it during observation.

## Redirects and Caddy-generated errors

Next16.4.6 config redirects discard accumulated custom response headers:
`resolve-routes.js` returns `resHeaders:null` in its config-redirect branch. Actual
local `/login`307 and `/uslugi`308 probes confirm this. Proxy response headers cannot
fix a redirect that resolves before Proxy. App-level headers also cannot cover
Caddy-generated errors or Cloudflare-owned block/error responses.

The **review-only** `.deployment/Caddyfile.security-headers.fragment` supplies
deferred defaults in the existing public/www block, plus that block's error route.
`?Header` preserves upstream values and adds only absent fields. The fragment does
not set an enforcing CSP, modify any guard/import/upstream, or define another host.
The error route explicitly reapplies the existing noindex/no-store values: a local
upstream-failure control confirmed that Caddy does not inherit the outer deferred
privacy headers into that separate route.
Its error handler uses an empty body and retains the error status. Compare that
behavior with the captured production error handling before adopting the fragment.

A local Caddy2.10 fixture validated and tested the fragment on nine responses:
200/307/308/400/403/404/502, including an upstream-failure fixture. Each requested
header occurs exactly once; optimized image sandbox CSP remains unchanged and502
retains an empty body. The app-only existing integration test retains all original
redirect status/location/privacy checks; its new app-header assertions explicitly
exclude307/308 because the separate edge layer is required there.

**Nothing imports or activates this fragment in production or the deployment
workflow.** A PR merge alone deploys the app headers; complete host/error/redirect
coverage also requires a separately approved Caddy/profile operation:

1. Recheck the exact live source, active JSON, mounts, helper/config hashes and
   public guard. Stop on drift or an existing public error handler needing a merge.
2. Make fresh root-only source/active/autosave/import/mount/profile backups.
3. Insert only the reviewed fragment inside the captured apex/www block. Require
   byte-identical source outside that block and unchanged peer/token/worker checks.
4. Validate/adapt the complete candidate, protected-host routes and guarded fallback.
   The existing deployment helper pins a normalized Caddy baseline, so review and
   explicitly approve its new profile baseline before allowing a subsequent release.
   Do not bypass that check or silently update its hash.
5. After owner approval, reload through the controlled procedure and run real edge,
   redirects/error, direct-origin IPv4/IPv6 and protected-service checks. Use the
   prepared guarded rollback on failure. No global Caddy/Cloudflare change is needed.

Cloudflare-owned redirects/errors may be produced before Caddy and still need
separate host-scoped response-transform review if coverage of those responses is
required. Global HSTS and includeSubDomains remain explicitly out of scope.
